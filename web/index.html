01 / Proof, not promises

A claim becomes a traceable decision.

Watch the route from written criteria to public evidence, validator assessment and a recorded verdict. Every step has a different responsibility—and a different limit.

01 — SPECIFICATION

Make the promise testable.

A funder defines explicit public checks before work begins. A successful milestone must satisfy those checks—not someone's subjective impression.

02 — EVIDENCE

Point to something real.

The builder publishes verifiable sources: a repository file, GitHub release, live page or documented deliverable. The sources remain inspectable.

03 — ASSESSMENT

Let validators examine it.

GenLayer validators independently evaluate the public sources. PASS and FAIL are distinct from ERROR, which means the source could not be read.

04 — RECORD

Keep the decision inspectable.

After the challenge window, finalization reassesses sources and records the application verdict. The Builder Delivery Record accepts Factory-created milestones.

How it works

One milestone, four moves

The funder writes the checks

A release tag, a file that must say something, a page that must be live, or a claim a page must support. All public, all fixed before the work starts.

readme  REPO_FILE   README.md contains "Honest limits"
site    LIVE_PAGE   the site answers 200 and says "Did they deliver?"

The builder ships

Anyone can open the milestone and see exactly what is being checked, with no account needed to look.

deadline: end of 2026-10-31 (UTC)
builder:  0xabF2…1160

Validators read the evidence

Each validator fetches the sources itself. Plain facts must match exactly, and a failing check is shown, never hidden. A source that is down shows ERROR, not FAIL.

readme  PASS
site    PASS
skill   PASS   → provisional MET

A window, then a verdict

The builder may point a failing check at the right place, only that, at most three times. After the window anyone can finalize, and finalizing re-reads every source.

START → ASSESS → (challenge window) → FINALIZE
verdict MET · finalized · on the record

What is different

Built for the question grants actually ask

Checks you can open yourself

Every check names its source. The verdict card shows each result next to what was read, so nobody has to trust a summary.

A fair window

A provisional reading can be answered once, and only by moving where a failing check looks. Never the criteria.

No typed verdicts

The factory deploys each milestone and reads its result back itself.

Honest about its limits

MET means the stated public checks held, not that the work is good. Test network, test accounts, one record so far. We say so on every verdict card.

Every finalized verdict adds to a record

A single verdict answers one question. A record answers the next one: has this builder kept their word before?

Milestones created through the factory are the only ones the record accepts, and the factory reads each verdict back from the milestone contract. Nobody types a result in.

Look up a builder

What a record line says

Who funded it, who built it, which checks held, how many times the builder amended where a check looks, and when it was finalized.

What it does not say

That the work was good, that the funder was fair, or that one person is behind one address. Treat a record as one input, not a credit score.

Questions

Who decides the verdict?

GenLayer validators. Each one fetches the public sources itself and they have to agree. No person, including us, can set a verdict.

What if a source is down?

That check shows ERROR. An error is never counted as a failure of the work; the round can be repeated.

Can the builder change the goalposts?

Only the place a failing check looks (for example a corrected tag), at most three times, with a written note. The funder cannot amend, and every change is in the history.

Does it hold or move money?

No. It records a verdict. Whatever you do with the verdict, such as releasing a grant payment, happens elsewhere.

What are the limits?

MET means the stated public checks hold, not that the work is good. Current-state verification: REPO_FILE, LIVE_PAGE and DELIVERABLE read evidence now, not as of the deadline. MET does not prove historical delivery. GITHUB_RELEASE compares the reported publication time; it does not freeze release contents. The record is small while the project is new, and test accounts can be one person. This runs on a test network.
